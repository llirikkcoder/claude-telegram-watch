# telegram-watch

Плагин для Claude Code: показывает в строке статуса, **доходят ли сообщения Telegram-канала до этой сессии**, и чинит конфликт нескольких экземпляров бота.

## Зачем

Плагин `telegram` устанавливается глобально, поэтому **каждая сессия Claude поднимает свой экземпляр бота**. Telegram отдаёт long polling ровно одному клиенту — значит два открытых окна означают два поллера на одном токене, и сообщения достаются то одному, то другому.

Снаружи это выглядит как «бот отвалился»: процесс жив, токен рабочий, человек в allowlist, а ответов нет. Проверка токена, `getMe` и `access.json` ничего не показывают — они всегда в порядке.

Второй случай тоньше: бот работает, но принадлежит **другому** окну. Тогда в текущей сессии канал молчит, что бы вы ни делали, — и обычный индикатор «процесс жив» бодро показывает, что всё хорошо.

## Что показывает

| Строка | Что значит |
|---|---|
| `tg ✓` | Бот поднят этой сессией, сообщения приходят сюда |
| `tg ⚠ в другой сессии` | Бот жив, но апдейты идут в другое окно Claude |
| `tg ✗ 2 инстанса — конфликт` | Два поллера на одном токене, сообщения теряются |
| `tg ✗ завис (N% CPU)` | Экземпляр крутит цикл переподключения и апдейты не забирает |
| `tg ✗ не запущен` | Канал не поднят |
| `tg ⚠ pid разошёлся` | Работающий процесс не тот, что записан в `bot.pid` |

Проверка укладывается в ~50 мс и **не ходит в `api.telegram.org`** — только `ps` и чтение файла. Иначе строка статуса била бы по Telegram на каждую отрисовку.

## Установка

```
/plugin marketplace add /Users/omoto/Projects/claude-plugins
/plugin install telegram-watch@local
```

Либо, если каталог перенесён, — укажите путь к нему.

## Подключение строки статуса

Плагин не может прописать `statusLine` сам: это пользовательская настройка. Добавьте в `~/.claude/settings.json`:

```json
{
  "statusLine": {
    "type": "command",
    "command": "/Users/omoto/Projects/claude-plugins/telegram-watch/scripts/statusline.sh",
    "padding": 0
  }
}
```

Строка покажет каталог, модель и состояние канала: `_DEMKOVICH · Opus 5 · tg ✓`.

Если у вас уже есть своя строка статуса — вызовите из неё `scripts/tg-status.sh` и подставьте вывод, он печатает только состояние канала одной строкой.

## Команды

**`/tgbot`** — разобраться, что с каналом: собирает процессы, `bot.pid`, состояние и объясняет, что означает увиденное.

**`/tg-set`** — узнать, какая сессия держит канал, и забрать его сюда.

Показывает владельца так, чтобы его можно было найти среди десятков открытых окон: номер терминала (`ttys028`), рабочий каталог, время запуска. С `--take` снимает чужой экземпляр.

Важное ограничение, проверенное на практике: **освободить канал команда может, а занять — нет.** Экземпляр бота поднимает MCP-клиент сессии при подключении, а не команда извне; после снятия чужого процесса новый сам не появляется. Поэтому порядок такой: `/tg-set --take`, затем `/mcp` и переподключить telegram — либо перезапустить сессию.

**`/tg-fix`** — снять конфликт: оставляет один экземпляр, остальные убирает. Сначала показывает вхолостую, кого снял бы, и помечает причину — «сирота от закрытого окна», «завис (N% CPU)» или просто «лишний поллер».

Осиротевшие и зависшие снимаются сразу — это мусор. А вот «лишний поллер» принадлежит другому вашему окну: команда спросит, прежде чем убивать, потому что там канал замолчит до перезапуска.

**`/tg-remember`** — устанавливает в память текущего проекта отдельную заметку: отвечать на Telegram-сообщения нужно только вызовом `reply`-инструмента, обычный текст в терминале до собеседника не доходит. Это не про конфликт поллеров — другой класс проблемы (см. ниже), но заметка ложится рядом, потому что ловится в той же среде и по тем же логам.

**Устанавливается не автоматически.** У плагинов Claude Code нет postinstall-хука — заметка не появится в памяти сама по себе после `/plugin install`. Нужно явно запустить `/tg-remember` в каждом проекте, где это актуально, один раз. Если этого не сделать, память проекта останется без заметки и сработавший однажды баг может повториться незамеченным.

Скрипты работают и без Claude Code:

```
scripts/tg-status.sh            # одна строка состояния
scripts/tg-set.sh               # кто держит канал: терминал, каталог, время
scripts/tg-set.sh --take        # освободить канал для этой сессии
scripts/tg-fix.sh --dry-run     # показать, кого снял бы
scripts/tg-fix.sh               # снять лишние
```

## Чего плагин не делает

Не управляет доступом к боту — этим занимается `/telegram:access` из основного плагина. Не поднимает канал: экземпляр появляется, когда сессия запущена с `--channels plugin:telegram@claude-plugins-official`.

Не чинит и не следит за тем, доходит ли конкретный *ответ* до собеседника — это не инфраструктурная проблема (два поллера на одном токене), а поведенческая: ассистент может ответить обычным текстом в терминале вместо вызова `reply`, и это выглядит как нормальный диалог по логу сессии, хотя в Telegram ничего не пришло. `/tg-remember` кладёт в память проекта заметку про этот случай, но не проверяет его автоматически — заметка работает только если её при работе действительно перечитывают.

## Как избежать проблемы вовсе

Держать канал в одном окне. Конфликт возникает ровно тогда, когда открыто второе, — и с этим плагином вы увидите это сразу, а не по молчанию собеседника.

Если окон много и непонятно, где именно сидит канал, — `/tg-set` назовёт терминал и каталог.
